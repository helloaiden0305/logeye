## 📖 简介

**logeye**（/lɒɡ aɪ/）是一套专为 **Android 系统稳定性分析** 设计的 Claude Code Skill 套件，基于 Log 分析经验沉淀而成。

核心价值：
- 🚀 **更快**：动态关键词生成，自动匹配历史模式
- 🎯 **更准**：内置反模式清单，置信度量化，避免误判
- 📊 **更全面**：支持多日志关联分析，代码级定位

## 📋 支持的日志类型

| 类型 | 特征 | 分析重点 |
|------|------|---------|
| **logcat** | `MM-DD HH:mm:ss.mmm PID TID` | 异常堆栈、系统事件、Binder 调用 |
| **kernel/dmesg** | `[` 开头的数字时间戳 | 进程被杀、OOM、thermal、调度 |
| **tombstone** | `signal` + `backtrace` + `Register` | Native 崩溃、SIGSEGV、SIGABRT |
| **traces.txt** | `"main" prio=` + `at android.` | Java 线程堆栈、死锁、ANR |
| **bugreport** | `DUMP OF SERVICE` | 系统全状态 |
| **rillog** | `AT+` / `RILC` / `RILJ` | 通话信令、SIM、网络注册 |
| **crash log** | `FATAL EXCEPTION` | Java 异常、崩溃堆栈 |

## 🔍 支持的问题类型

| 问题类型 | 关键词 |
|---------|--------|
| 无响应/ANR | 卡死、无响应、冻住、不动、不响应 |
| 崩溃/闪退 | 崩溃、闪退、停止运行、crash |
| 系统级 | 重启、关机、死机 |
| UI 渲染 | 显示异常、花屏、白屏、错位 |
| 音频/通话 | 声音、无声、通话、蓝牙 |
| 网络 | 网络、断网、连接失败 |
| 性能 | 发热、耗电、卡顿、慢 |
| 安装/启动 | 安装失败、无法打开 |

## ⚠️ 常见误判清单

| 误区 | 正确做法 |
|------|---------|
| 看到 ANR 就查主线程 | 也要看 Binder 对端服务是否卡住 |
| 看到 crash 就修 crash | crash 可能是其他问题的结果 |
| 只看 ERROR 级别日志 | 有时关键信息在 WARN 甚至 INFO |
| 看到 LOW_MEMORY 就认为是内存问题 | LOW_MEMORY 可能是结果不是原因 |
| Widget 无响应就是 Widget 问题 | 可能是 SystemUI/Launcher 崩溃导致 |

## 📥 日志采集指南

### 标准采集命令

**logcat 日志（推荐）：**
```bash
# 采集所有级别日志，保存为文件
adb logcat -v threadtime > logcat_$(date +%Y%m%d_%H%M%S).txt

# 指定时长采集（如 60 秒）
timeout 60 adb logcat -v threadtime > logcat_60s.txt

# 采集后清空缓冲区（下次复现用）
adb logcat -c
```

**tombstone（Native 崩溃）：**
```bash
# 拉取所有 tombstone 文件
adb pull /data/tombstones/ ./tombstones/

# 查看最新 tombstone
adb cat /data/tombstones/tombstone_01
```

**traces.txt（ANR）：**
```bash
# ANR 发生时自动保存在/data/anr/
adb pull /data/anr/traces.txt ./traces_$(date +%Y%m%d_%H%M%S).txt
```

**kernel/dmesg（内核日志）：**
```bash
adb shell dmesg > dmesg_$(date +%Y%m%d_%H%M%S).txt
```

### 采集要求

| 要求 | 说明 |
|------|------|
| **时间范围** | 问题发生前后至少 5 分钟，建议 10 分钟 |
| **日志级别** | 包含 V/D/I/W/E 所有级别，不要过滤 |
| **时间戳格式** | 使用 `-v threadtime` 显示线程和时间 |
| **完整性** | 包含问题触发点、传播过程、最终现象 |
| **多进程** | 如涉及跨进程问题，确保覆盖所有相关进程 |

### 常见问题

**Q: 日志太大怎么办？**
A: 优先保证时间完整性，logeye 能处理 10 万 + 行日志。如确实过大，可分段采集。

**Q: 只能提供部分日志可以吗？**
A: 可以，但可能影响分析准确性。建议提供完整时间窗口。

**Q: 没有 adb 权限怎么办？**
A: 使用系统自带日志导出功能，或请测试同学协助采集。

## ❓ FAQ

### Q1: logeye 能解决所有问题吗？

**不能**。logeye 擅长分析**有日志可查**的系统稳定性问题，以下场景不适用：
- 硬件问题（屏幕坏点、按键失灵）
- 纯代码逻辑 bug（需要代码审查）
- 实时监控（只能离线分析）
- 无法复现且无日志的问题

### Q2: 分析准确率有多高？

综合准确率约 **90%+**，基于 32 个已验证模式。置信度说明：
- **90%+**: 有完整证据链 + 日志明确指向
- **70-90%**: 有间接证据 + 逻辑推理合理
- **50-70%**: 有推测但无法完全验证
- **<50%**: 信息不足，仅方向性建议

### Q3: 新人多久能上手？

**1 周**即可独立使用。logeye 将 3-6 个月的经验积累压缩为模式库，新人直接复用即可。

### Q4: 如何贡献新模式？

发现新场景后：
1. 确认不是已有模式的变体
2. 提取关键特征和根因链条
3. 追加到 `logeye_patterns.md`「正模式」区
4. 更新模式索引表格

### Q5: 分析失败怎么办？

如 logeye 无法定位根因：
1. 检查日志完整性（是否覆盖问题全过程）
2. 查看报告中的"待补充信息"建议
3. 考虑是否属于 logeye 边界外问题
4. 转人工分析或联系音频/相机等专项团队

## ⚠️ 无法诊断提示

如遇到以下情况，logeye 将明确告知"无法诊断"并给出建议：

| 情况 | logeye 响应 |
|------|------------|
| 日志未覆盖问题时间点 | "日志时间范围未覆盖问题发生时刻，建议补充 xx:xx-xx:xx 的日志" |
| 日志类型不匹配 | "当前日志为 logcat，但此类问题需要 tombstone/traces.txt，建议补充" |
| 问题描述过于模糊 | "请描述具体现象（如'点击 xx 按钮后 xx 无响应'），而非'感觉有问题'" |
| 属于硬件/代码逻辑问题 | "此类问题需要代码审查/硬件检测，日志分析无法定位根因" |
| 偶现问题无现场日志 | "当前日志未捕获问题现场，建议复现后提供完整日志" |
